# ADR 0003：开放接口凭证是「租户级无状态主体 + 精确权限集合」

- 日期：2026-10-10
- 状态：已采纳

## 背景

附录 F 的 `sys_api_key` 只说存 `scopes`（「允许的权限标识/接口范围」）。需要决定：
凭证请求的 `Principal` 是什么、`scopes` 怎么参与权限判定、数据范围给多大。

## 结论

- 认证走 `X-API-Key`（与 `Authorization: Bearer` 二选一，Bearer 优先），**不建会话**：
  每次请求按 `key_prefix` 命中候选、验 Argon2id 哈希、检查状态与有效期。
- 主体是租户级主体：`user_id = 0`、`session_id = apikey:<id>`、`user_name` 取凭证名，
  `is_super_admin = false`。因此凭证不会被误认为「某个人」，也不会获得超管的跨租户特权。
- `scopes` 是**精确匹配**的权限标识列表，直接进 `RequestContext.permissions`，
  受同一套路由权限守卫约束（`*` 不做通配展开，避免语义歧义）。
- 数据范围固定 `DataScope::all()`（租户内全部）。凭证本来就是租户级凭据；
  要更细的可见性，应走用户令牌 + 角色数据范围。
- 停用/删除后立即失效（无状态鉴权的代价是每次查库，这正是要验证的行为）。

## 代价

- 每个 API 请求多一次 `sys_api_key` 查询（前缀索引 + 单条哈希校验）；高频场景可加进程内缓存 +
  版本号失效（与 §7.3 的缓存模型一致），当前未做。
- 凭证明文不可恢复：丢失只能重新签发。
